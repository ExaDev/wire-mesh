# conformance/

Golden test vectors: every implementation's CI must decode each vector's `wire_hex` to its `message` and re-encode `message` back to exactly `wire_hex`. This is the actual forcing function against drift between implementations -- a schema alone never proves interop, only shared vectors do, the same lesson Cascade's own `docs/conformance/*.v1.json` was built to enforce for its XDR-based protocol.

`mint.v1.json` covers the minting of capability tokens and revocation entries (see below). `handshake.v1.json` covers `handshake-frame`. `tokens.v1.json` covers `capability-token` (including a delegation chain, one token's `parent` pointing at another) and `handle-record`. `frames.v1.json` covers every other `$frame-variant` in `spec/frame.cddl`. `adverts.v1.json` covers `peer-advert` on its own. `secure-channel.v1.json` covers the secure channel's hellos and sealed frames and the cryptography around them. `invalid-frames.v1.json` covers frames a decoder must refuse.

`invalid-frames.v1.json` holds values outside the grammar of the spec's `.regexp` patterns, which match the whole string: a capability verb with two colons, a trailing space or newline or a leading hyphen, a domain with trailing text, a trailing newline or an embedded separator, and the three verb fields of token claims (`capability`, `grants-capability`, `requests-capability`). Each vector is well-formed CBOR in the shape of a valid frame (`kind: "frame"`) or token-claims map (`kind: "token-claims"`) with exactly one such value, so a conformant decoder refuses it at decoding or at validation. It carries `refused: true`, the rule it breaks in `pattern`, and `valid_control_wire_hex`, the same bytes with a value inside the grammar, which every consumer must accept, so a vector cannot be refused for any other reason than its pattern. `message` and `wire_hex` follow the shared round-trip contract, so the round-trip suites read it like any other file. The TypeScript core's conformance test and `rust/crates/wire-mesh-conformance` both check the refusal and the control. The same invalid capability verbs are sealed in `secure-channel.v1.json` (`undecodable_invalid_*capability_verb_*`), where the frame authenticates, is refused as `undecodable` and consumes its counter. The room-path and device-id-hex patterns occur only in room-notice claims; the implementations' own schema and parser tests pin them, edge by edge.

`adverts.v1.json` is the one file built on real cryptographic material rather than structural filler, and the one whose vectors carry more than a round trip. A peer-advert's signature is the only thing binding a gossiped device-id to the device that owns it (`spec/transport.cddl`), so each vector also records `signing_input_hex`, the exact bytes that signature covers, and `verifies`, the verdict a conformant verifier must reach. Two implementations that reconstruct the signing input even one byte differently reject each other's every advert while each passes its own tests, which is precisely the failure a frozen byte string turns into a failing vector. Ed25519 rather than ES256, from a fixed seed, because its signatures are deterministic (RFC 8032) and CI regenerates this file and diffs it against the committed copy. It also holds adverts whose identity key or signature a verifier must refuse though a lax one would accept it (`peer_advert_v1_signature_*`, `peer_advert_v1_identity_key_*` and `peer_advert_v1_es256_*`): the Rust binary reads this file, so these pin it, and the TypeScript test checks each verdict. The Ed25519 ones are built with the group arithmetic in `ed25519-arithmetic.ts` and the ES256 ones with the deterministic ECDSA in `p256-arithmetic.ts`.

`secure-channel.v1.json` pins `spec/secure-channel.cddl`: the handshake, the key schedule and the sealing of data frames. Its top-level `vectors` are every hello and every sealed `secure-data` frame in the transcripts, round-tripped like any other file. Its `secure_channel` section holds what a round trip cannot, and carries its own `layout_version` (the version of the section's layout, separate from `protocol_version`):

- `identities`: an Ed25519 seed or ES256 scalar (`secret_hex`, which one depends on `alg`), public key and device-id for each, every entry marked `synthetic: true`.
- `handshakes`: each side's fixed ephemeral scalar, public point and nonce, the hello's signing input and signature (`signature_verify_only` is true for ES256), then the shared secret, salt, both HKDF infos and both direction keys, and a transcript of sealed frames with each IV, associated data and ciphertext.
- `hello_verdicts`: the reason a receiver gives for each hello, one of `ok`, `wrong_recipient`, `unsupported_identity_alg`, `invalid_identity_key` or `bad_signature`. A vector has exactly one answer, and a consumer refuses a hello verdict that carries any other field. Two orders are pinned: the recipient before the identity-key checks, and key usability before the signature. An identity key's bytes are pinned for both algorithms (`spec/identity.cddl`): every Ed25519 small-order point, non-canonical encodings, a key with a torsion component, and the ES256 compressed, compact, point-at-infinity and zero-point keys are `invalid_identity_key`, each hello signed so that the signature would verify where one can; and an Ed25519 signature with S not reduced, with R of small order, not canonical or with a torsion component, under a usable key, is `bad_signature`. The ES256 handshake adds a DER-encoded signature (`bad_signature`) and a signature with s in the high half (`ok`, because the spec says a verifier MUST accept either form).
- `establish_verdicts`: hellos that verify as hellos (`hello_verdict: "ok"`) but carry an ephemeral key that cannot be used. A key of the right length that is not on the curve is `unusable_ephemeral_key`, refused when the channel is established. A key in another encoding (identity, compressed, missing prefix, wrong length) is `refused`, at decoding or at establishment: `stage_advisory` is true, since the spec says the stage is not part of the contract.
- `open_sequences`: secure-data frames to open in order on a fresh channel, each step expecting the opened frame or one of `replayed`, `unauthentic` and `undecodable`. Replay is checked before authentication and authentication before decoding. An `undecodable` frame consumes its counter, which each such sequence shows by following it with the genuine frame at that counter (`replayed`) and the next counter (opened); a replayed or unauthentic frame changes nothing.

The negative sequences each differ from a genuine frame in one input, except `reflected_frame`, which is the receiver's own frame sent back at it and so differs in the key and in the associated data. They are a tampered ciphertext byte, tag byte, counter or associated data, a truncated tag, a ciphertext shorter than a tag, an empty ciphertext, the other direction's key (`wrong_direction_key`), a frame from another channel between the same devices, a replayed counter, an altered frame at a counter already passed, an out-of-order counter, a forged high counter that must not lock out genuine frames, and authenticated plaintexts that are not one frame (an unknown type, missing fields, a non-shortest length, an indefinite-length map, trailing bytes, nothing). `kind_outside_obligation_5` seals a `ping`: it opens at the channel, and spec obligation 5 has the receiver drop it afterwards (`receiver_drops_after_open`); the spec states no rule for a sender.

The counter is an unsigned 64-bit integer and the vectors tell a wrong width or layout apart: `counter_in_every_low_byte` and `largest_exact_counter` (2^53 - 1) open on a JavaScript implementation, and `counter_beyond_exact_range`, `counter_with_a_distinct_byte_in_all_eight_positions` and `largest_counter` (2^64 - 1) need a full 64-bit counter. A step with `full_width_only: true` is one an implementation with a narrower counter must refuse and must not truncate (spec, counter paragraph); such an implementation skips the steps after it in the sequence. Every counter in the section is a decimal string, since JSON numbers cannot hold a 64-bit value, and every optional flag or value is present (`false`, `[]` or `null` when it does not apply). A step's `counter` and the counter inside its `secure_data_wire_hex` are generated from one value and agree; a consumer reads the wire bytes, and the `counter` string saves it decoding them to name the step.

The expected class of every step is part of the file: an implementation that reports only opened or not is not checking it. A refusal's stage is part of the contract only where `stage_advisory` is false. The sender rule (a sender refuses to seal once its next counter would exceed what it can hold, and never wraps) is not a vector, since a vector cannot express a refusal to produce; it is checked in each implementation's own tests (`claimSendCounter` and the sealing and relay-channel tests in `ts/packages/core`, and the `SecureChannel::seal` tests in `wire-mesh-core`).

What the TypeScript test (`ts/packages/core/test/conformance-secure-channel.unit.test.ts`) checks, against the real `verifyHello`, `establishChannel`, `seal` and `open` plus test-only `node:crypto` and Web Crypto derivations: every field of the section except the labels that only name things (`name`, `inner_frame`, `sealed_vector`, `hello_vector`). That includes each identity's public key and device-id derived from its seed or scalar, every hello signing input, every Ed25519 signature (reproduced), the shared secrets, salts, HKDF infos and both direction keys, every IV and associated data, every ciphertext, every hello reason and open class, and the step counters against their wire bytes. Its schemas are strict, so a key it does not read fails it. Not checked there: an ES256 signature (verified, never reproduced), and for a `full_width_only` step above the 2^53 - 1 bound, the expected class (only that the frame is refused at decoding), and the steps after it.

Every key in the file is made up for the vectors and is test material only. Ed25519 signatures and AES-GCM are deterministic, so regenerating reproduces them byte for byte. ES256 signatures are not, so a hello signed that way (`signature_verify_only`) is verify-only: an implementation checks that its signature verifies and never expects to reproduce it. The generator reads the committed file when it runs. Where an ES256 hello's signing input is unchanged and its committed signature still verifies, that signature is kept; otherwise (the file absent, as in a clean tree, or the input changed) a fresh one is made and everything derived from it, the DER and high-s forms, changes with it. CI runs the generator with the committed file present and diffs the result against it, so it covers the first case; a regeneration from a clean tree is not reproducible for the ES256 hellos and is not what CI checks.

The generator computes the cryptography (key agreement, HKDF, AES-GCM, signatures) with `node:crypto`, written from the spec text and importing neither implementation, so for those layers it is independent of the TypeScript core's Web Crypto use and of any other implementation. It is not independent for the CBOR layer: it encodes with `cbor2` through `codec.ts`, the same library the TypeScript core uses, so a canonical-encoding bug in `cbor2` would be reproduced by both. An implementation on another CBOR library is the independent check there.

Every `conformance/*.v1.json` is accounted for by each harness that reads this directory by listing it, never by a hand-written list a new file could be missing from. `verify.unit.test.ts` round-trips every file and fails on a top-level key nothing is registered to check; `ts/packages/core/test/conformance.unit.test.ts` fails on a file that is neither in its own list nor registered against a test file that exists (it does not read that test, so the registration is a claim a reviewer checks); and `rust/crates/wire-mesh-conformance` fails on a file that it does not check and does not list, with the issue that tracks it, as not yet consumed.

`verify.unit.test.ts` checks only the round trip every vector file shares: this package holds no protocol implementation of its own, so `signing_input_hex`, `verifies` and the `secure_channel` section are checked by the implementations. `ts/packages/core`'s own conformance tests check them for the TypeScript. The Rust binary checks every file: the round trip of each, `adverts.v1.json`'s extra fields, and `secure-channel.v1.json`'s `secure_channel` section, which it recomputes from the fixed inputs and runs step by step against `wire_mesh_core::domain::secure_channel` (the intermediate keys, every sealed ciphertext, every verdict and every open step with its expected class), failing on any field of the section it does not read.

## Regenerating

```
pnpm install
pnpm run generate   # rebuilds codec.ts first, then writes {handshake,tokens,adverts,frames,secure-channel}.v1.json from generate.ts's vector definitions
pnpm test            # rebuilds codec.ts first, then decodes every committed vector and confirms it round-trips
```

`generate.ts` holds the vector definitions and is the actual source of truth, not the JSON files; `adverts.ts` holds `adverts.v1.json`'s own, which need real key material rather than filler, `secure-channel-vectors.ts` holds `secure-channel.v1.json`'s, and `vector-files.ts` holds the writer and each output file's description. All three are split apart because generate.ts sits at this repo's own max-lines cap, not because they are conceptually separate stages: every vector's `message` is authored as plain TypeScript data matching a CDDL rule's fields, and `wire_hex` is derived mechanically by canonically CBOR-encoding it via [`cbor2`](https://www.npmjs.com/package/cbor2)'s CDE (CBOR Common Deterministic Encoding) mode -- the RFC 8949 4.2 core deterministic rules DAG-CBOR itself builds on -- never hand-typed. CI regenerates and diffs against the committed files the same way `spec/`'s own `cddl-validate` job does for `protocol.cddl`, so the two can never silently drift apart.

## Tasks, caching, and linting

`build`/`generate`/`test`/`typecheck`/`lint` are each a thin public script that calls `turbo run _<name>` -- e.g. `"build": "turbo run _build"`, `"_build": "tsdown"`. `turbo.json` keys its task graph on those same underscore names (never the public ones: a task literally named `build` would make `pnpm run build`'s own `turbo run build` call resolve straight back to itself, the recursive-call case Turborepo's docs warn against). `generate`/`test`/`typecheck`/`lint` all depend on `build`, so any of them rebuilds `codec.ts` first when something it depends on changed, and replays the cached result when nothing did -- running several in one invocation (`pnpm turbo run _generate _test _typecheck _lint`, what `just conformance` does) still only builds once, deduplicated across every task that needs it.

Linting uses [`@exadev/eslint-config`](https://www.npmjs.com/package/@exadev/eslint-config), the org's shared config, plus Prettier via `eslint-plugin-prettier`. Typed lint rules need `dist/`'s declarations to resolve the self-referenced package import, which is exactly why `_lint` depends on `_build` too.

## codec.ts is a real, polymorphic package, not just a shared file

`codec.ts` defines the one JSON convention every vector's `message` needs: since JSON has no byte-string type, a CDDL `bstr` field is written as `{ "hex": "<lowercase hex>" }` rather than a raw string or number array. `toWire`/`fromWire` convert between that marker shape and the real bytes CBOR needs on the way in and out; `isVectorFile` validates a parsed vector file at the JSON boundary rather than trusting an `as` cast.

`generate.ts` and `verify.unit.test.ts` both import it as `@exadev/wire-mesh-conformance` (self-referencing the package by its own name), not via a relative path -- `pnpm run build` (`tsdown`) compiles `codec.ts` into dual ESM/CJS output plus `.d.mts`/`.d.cts` declarations under `dist/`, and `package.json`'s `exports` map is what makes the self-reference resolve to that built output rather than the source file. This means the same artifact every consumer would actually get is what runs here, not a stand-in. [`@arethetypeswrong/cli`](https://github.com/arethetypeswrong/arethetypeswrong.github.io) (wired into the `build` script via `tsdown`'s own `attw` option) checks that dual-package surface resolves correctly under Node's `node16` module resolution -- catching the class of "works in this repo, broken for a real consumer" bug that a bare `tsc` build can't see, before it ever has to matter.

Node (26+) runs every `.ts` file here directly via its own native TypeScript support -- no `tsx`/`ts-node` needed. `tsconfig.json` sets `moduleResolution: "nodenext"` to match that reality, and is scoped to `codec.ts` alone (`"include": ["codec.ts"]`) since that's the one file `tsdown` actually builds -- anything else in this scope (a script's own top-level await, a config file's own type shape) would otherwise leak into what gets type-checked as part of the *build*. Everything else (`generate.ts`, `verify.unit.test.ts`, `tsdown.config.ts`, `eslint.config.ts`) is covered by `tsconfig.node.json` instead, which extends `tsconfig.json`. `pnpm run typecheck` runs both.

Signature and public-key bytes throughout are clearly-synthetic filler (`aa`/`bb`/`ee`/`ff`-repeated hex), not real cryptographic material -- these vectors freeze the wire-exact envelope shape (map key ordering, field presence, the recursive delegation-chain nesting), not a working signature, the same scope Cascade's own frozen vectors commit to for fields with no real crypto behind them.

## Gotcha: `cbor2` doesn't recognise a Node `Buffer` as a byte string

Feeding a plain Node `Buffer` (rather than a plain `Uint8Array`) into `cbor2`'s `encode()` silently produces the wrong output: `Buffer` overrides `toJSON()`, and `cbor2`'s type dispatch falls through to a generic-object encoder that serialises it as a garbled `{ type: "Buffer", data: [...] }` CBOR map instead of a byte string, with no error raised. Confirmed directly while writing this generator -- caught only because the verifier's round-trip check failed with an unreadable diff. `toWire()` in `codec.ts` guards against this explicitly, converting every marker to a genuine `Uint8Array` via `Uint8Array.from(Buffer.from(hex, "hex"))` rather than passing a `Buffer` straight to `encode()`.

## Gotcha: `typescript` is pinned below 6.1, not left on latest

`typescript-eslint` (which `@exadev/eslint-config` depends on) does not yet support TypeScript 7 -- confirmed directly, `eslint` fails outright with "typescript-eslint does not support TS 7.0" against the latest `typescript` release. `typescript` is pinned to `6.0.3`, the newest release still inside `typescript-eslint`'s own `>=4.8.4 <6.1.0` peer range, rather than left on latest -- this is the documented-incompatibility exception the org's own dependency convention already carves out for exactly this situation. Bump it back to latest once [typescript-eslint#10940](https://github.com/typescript-eslint/typescript-eslint/issues/10940) ships support for TS 7.

## mint.v1.json

`mint.v1.json` pins what a conformant minter produces and refuses (`spec/tokens.cddl`, `spec/management.cddl`). Its top-level `vectors` are every minted token and revocation entry, round-tripped like any other file. Its `mint` section holds the inputs of each case and the expected outcome, with its own `layout_version`:

- `identities`: Ed25519 identities (`secret_hex`, public key and device-id, each marked `synthetic: true`), whose signatures are deterministic, so a minter given the same inputs produces the same bytes.
- `token_mints`: each case lists every input of a mint (issuer, clock, token-id, bearer, verb, scope, expiry, optional not-before, delegations-remaining, conditions, the whole COSE_Sign1 of a parent or an authorising grant-capability, grants-capability and requests-capability, with `null` for an absent optional) and expects either `minted` (the vector holding the exact token, and `verifies`, whether it verifies on its own at the file's clock) or `refused` with one reason. A refusal case breaks one rule, except `refused_bearer_before_expiry`, which breaks two to pin the order the checks run in.
- `revocation_mints`: the exact entry minted from an identity, a token-id and a revoked-at.
- `can_grant` and `can_grant_via`: the verdict of the two pure queries for a held token, a device and a candidate (and a bearer, for the authorised-by form).

A token's protected header carries its `alg` and `kid` under the text keys `"1"` and `"4"`, which is what the frozen vectors and the TypeScript core write and every verifier reads. The generator builds each token from the spec text with node:crypto alone, and the expected refusal of each case is written by hand, so the vectors check an implementation against the spec and not against itself. Each implementation's own tests check them: `ts/packages/core/test/conformance-mint.unit.test.ts` and `rust/crates/wire-mesh-conformance`.
