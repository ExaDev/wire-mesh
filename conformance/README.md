# conformance/

Golden test vectors: every implementation's CI must decode each vector's `wire_hex` to its `message` and re-encode `message` back to exactly `wire_hex`. This is the actual forcing function against drift between implementations -- a schema alone never proves interop, only shared vectors do, the same lesson Cascade's own `docs/conformance/*.v1.json` was built to enforce for its XDR-based protocol.

`mint.v1.json` covers the minting of capability tokens, revocation entries and room notices (see below). `handshake.v1.json` covers `handshake-frame`. `tokens.v1.json` covers `capability-token` (including a delegation chain, one token's `parent` pointing at another) and `handle-record`. `frames.v1.json` covers every other `$frame-variant` in `spec/frame.cddl`. `adverts.v1.json` covers `peer-advert` on its own. `secure-channel.v1.json` covers the secure channel's hellos and sealed frames and the cryptography around them. `invalid-frames.v1.json` covers frames a decoder must refuse. `coordinator-election.v1.json` covers the gossiped coordinator claims and the outcome of sequences of them. `data-sync.v1.json` covers the core/data have, request and entries exchange over a key-value store. `file-storage.v1.json` covers the on-disk layout of the file-backed key-value store. `gossip-directory.v1.json` covers what a session does with the gossip it receives and sends. `room-params.v1.json` covers the typed core/room and capability verbs and the room-path and hex helpers. `introspection.v1.json` covers core/management's `path:trace` and `topology.get` and the topology they report.

`invalid-frames.v1.json` holds values outside the grammar of the spec's `.regexp` patterns, which match the whole string: a capability verb with two colons, a trailing space or newline or a leading hyphen, a domain with trailing text, a trailing newline or an embedded separator, and the three verb fields of token claims (`capability`, `grants-capability`, `requests-capability`). Each vector is well-formed CBOR in the shape of a valid frame (`kind: "frame"`) or token-claims map (`kind: "token-claims"`) with exactly one such value, so a conformant decoder refuses it at decoding or at validation. It carries `refused: true`, the rule it breaks in `pattern`, and `valid_control_wire_hex`, the same bytes with a value inside the grammar, which every consumer must accept, so a vector cannot be refused for any other reason than its pattern. `message` and `wire_hex` follow the shared round-trip contract, so the round-trip suites read it like any other file. The TypeScript core's conformance test and `rust/crates/wire-mesh-conformance` both check the refusal and the control. The same invalid capability verbs are sealed in `secure-channel.v1.json` (`undecodable_invalid_*capability_verb_*`), where the frame authenticates, is refused as `undecodable` and consumes its counter. The room-path and device-id-hex patterns occur only in room-notice claims; the implementations' own schema and parser tests pin them, edge by edge.

`adverts.v1.json` is the one file built on real cryptographic material rather than structural filler, and the one whose vectors carry more than a round trip. A peer-advert's signature is the only thing binding a gossiped device-id to the device that owns it (`spec/transport.cddl`), so each vector also records `signing_input_hex`, the exact bytes that signature covers, and `verifies`, the verdict a conformant verifier must reach. Two implementations that reconstruct the signing input even one byte differently reject each other's every advert while each passes its own tests, which is precisely the failure a frozen byte string turns into a failing vector. Ed25519 rather than ES256, from a fixed seed, because its signatures are deterministic (RFC 8032) and CI regenerates this file and diffs it against the committed copy. It also holds adverts whose identity key or signature a verifier must refuse though a lax one would accept it (`peer_advert_v1_signature_*`, `peer_advert_v1_identity_key_*` and `peer_advert_v1_es256_*`): the Rust binary reads this file, so these pin it, and the TypeScript test checks each verdict. The Ed25519 ones are built with the group arithmetic in `ed25519-arithmetic.ts` and the ES256 ones with the deterministic ECDSA in `p256-arithmetic.ts`.

`secure-channel.v1.json` pins `spec/secure-channel.cddl`: the handshake, the key schedule and the sealing of data frames. Its top-level `vectors` are every hello and every sealed `secure-data` frame in the transcripts, round-tripped like any other file. Its `secure_channel` section holds what a round trip cannot, and carries its own `layout_version` (the version of the section's layout, separate from `protocol_version`):

- `identities`: an Ed25519 seed or ES256 scalar (`secret_hex`, which one depends on `alg`), public key and device-id for each, every entry marked `synthetic: true`.
- `handshakes`: each side's fixed ephemeral scalar, public point and nonce, the hello's signing input and signature (`signature_verify_only` is true for ES256), then the shared secret, salt, both HKDF infos and both direction keys, and a transcript of sealed frames with each IV, associated data and ciphertext.
- `hello_verdicts`: the reason a receiver gives for each hello, one of `ok`, `wrong_recipient`, `unsupported_identity_alg`, `invalid_identity_key` or `bad_signature`. A vector has exactly one answer, and a consumer refuses a hello verdict that carries any other field. Two orders are pinned: the recipient before the identity-key checks, and key usability before the signature. An identity key's bytes are pinned for both algorithms (`spec/identity.cddl`): every Ed25519 small-order point, non-canonical encodings, a key with a torsion component, and the ES256 compressed, compact, point-at-infinity and zero-point keys are `invalid_identity_key`, each hello signed so that the signature would verify where one can; and an Ed25519 signature with S not reduced, with R of small order, not canonical or with a torsion component, under a usable key, is `bad_signature`. The ES256 handshake adds a DER-encoded signature (`bad_signature`) and a signature with s in the high half (`ok`, because the spec says a verifier MUST accept either form).
- `establish_verdicts`: hellos that verify as hellos (`hello_verdict: "ok"`) but carry an ephemeral key that cannot be used. A key of the right length that is not on the curve is `unusable_ephemeral_key`, refused when the channel is established. A key in another encoding (identity, compressed, missing prefix, wrong length) is `refused`, at decoding or at establishment: `stage_advisory` is true, since the spec says the stage is not part of the contract.
- `open_sequences`: secure-data frames to open in order on a fresh channel, each step expecting the opened frame or one of `replayed`, `unauthentic` and `undecodable`. Replay is checked before authentication and authentication before decoding. An `undecodable` frame consumes its counter, which each such sequence shows by following it with the genuine frame at that counter (`replayed`) and the next counter (opened); a replayed or unauthentic frame changes nothing.

The negative sequences each differ from a genuine frame in one input, except `reflected_frame`, which is the receiver's own frame sent back at it and so differs in the key and in the associated data. They are a tampered ciphertext byte, tag byte, counter or associated data, a truncated tag, a ciphertext shorter than a tag, an empty ciphertext, the other direction's key (`wrong_direction_key`), a frame from another channel between the same devices, a replayed counter, an altered frame at a counter already passed, an out-of-order counter, a forged high counter that must not lock out genuine frames, and authenticated plaintexts that are not one frame (an unknown type, missing fields, a non-shortest length, an indefinite-length map, trailing bytes, nothing). `kind_outside_obligation_5` seals a `ping`: it opens at the channel, and spec obligation 5 has the receiver drop it afterwards (`receiver_drops_after_open`); the spec states no rule for a sender.

The counter is an unsigned 64-bit integer and the vectors tell a wrong width or layout apart: `counter_in_every_low_byte` and `largest_exact_counter` (2^53 - 1) open on a JavaScript implementation, and `counter_beyond_exact_range`, `counter_with_a_distinct_byte_in_all_eight_positions` and `largest_counter` (2^64 - 1) need a full 64-bit counter. A step with `full_width_only: true` is one an implementation with a narrower counter must refuse and must not truncate (spec, counter paragraph); such an implementation skips the steps after it in the sequence. Every counter in the section is a decimal string, since JSON numbers cannot hold a 64-bit value, and every optional flag or value is present (`false`, `[]` or `null` when it does not apply). A step's `counter` and the counter inside its `secure_data_wire_hex` are generated from one value and agree; a consumer reads the wire bytes, and the `counter` string saves it decoding them to name the step.

The expected class of every step is part of the file: an implementation that reports only opened or not is not checking it. A refusal's stage is part of the contract only where `stage_advisory` is false. The sender rule (a sender refuses to seal once its next counter would exceed what it can hold, and never wraps) is not a vector, since a vector cannot express a refusal to produce; it is checked in each implementation's own tests (`claimSendCounter` and the sealing and relay-channel tests in `ts/packages/core`, and the `SecureChannel::seal` tests in `wire-mesh-core`).

What the TypeScript test (`ts/packages/core/test/conformance-secure-channel.unit.test.ts`) checks, against the real `verifyHello`, `establishChannel`, `seal` and `open` plus test-only `node:crypto` and Web Crypto derivations: every field of the section except the labels that only name things (`name`, `inner_frame`, `sealed_vector`, `hello_vector`). That includes each identity's public key and device-id derived from its seed or scalar, every hello signing input, every Ed25519 signature (reproduced), the shared secrets, salts, HKDF infos and both direction keys, every IV and associated data, every ciphertext, every hello reason and open class, and the step counters against their wire bytes. Its schemas are strict, so a key it does not read fails it. Not checked there: an ES256 signature (verified, never reproduced), and for a `full_width_only` step above the 2^53 - 1 bound, the expected class (only that the frame is refused at decoding), and the steps after it.

Every key in the file is made up for the vectors and is test material only. Ed25519 signatures and AES-GCM are deterministic, so regenerating reproduces them byte for byte. ES256 signatures are not, so a hello signed that way (`signature_verify_only`) is verify-only: an implementation checks that its signature verifies and never expects to reproduce it. The generator reads the committed file when it runs. Where an ES256 hello's signing input is unchanged and its committed signature still verifies, that signature is kept; otherwise (the file absent, as in a clean tree, or the input changed) a fresh one is made and everything derived from it, the DER and high-s forms, changes with it. CI runs the generator with the committed file present and diffs the result against it, so it covers the first case; a regeneration from a clean tree is not reproducible for the ES256 hellos and is not what CI checks.

The generator computes the cryptography (key agreement, HKDF, AES-GCM, signatures) with `node:crypto`, written from the spec text and importing neither implementation, so for those layers it is independent of the TypeScript core's Web Crypto use and of any other implementation. It is not independent for the CBOR layer: it encodes with `cbor2` through `codec.ts`, the same library the TypeScript core uses, so a canonical-encoding bug in `cbor2` would be reproduced by both. An implementation on another CBOR library is the independent check there.

Every `conformance/*.v1.json` is accounted for by each harness that reads this directory by listing it, never by a hand-written list a new file could be missing from. `verify.unit.test.ts` round-trips every file and fails on a top-level key nothing is registered to check; `ts/packages/core/test/conformance.unit.test.ts` fails on a file that is neither in its own list nor registered against a test file that exists (it does not read that test, so the registration is a claim a reviewer checks); and `rust/crates/wire-mesh-conformance` fails on a file that it does not check and does not list, with the issue that tracks it, as not yet consumed.

## coordinator-election.v1.json

`coordinator-election.v1.json` pins the rules of the gossiped, term-based election (`coordinator-frame` in `spec/transport.cddl`). Its top-level `vectors` are every claim a scenario gossips, round-tripped like any other file. Its `coordinator_election` section carries its own `layout_version` and holds:

- `scenarios`: each starts a side (`own_device_hex`) that has made and heard no claim, then runs `steps`. A step is `evaluate` (a frame heard, by vector name; the expected `outcome` is `accepted`, `retained` or `rejected`, with the incumbent returned), `claim` (the side makes its own claim at a capacity hint; it expects the frame to gossip, or a refusal when no term is left) or `announce_current` (the incumbent's frame, or none). Every step also records the `state` after it: the incumbent (`current`) and whether it is the side's own device.
- `refused_claims`: a claim made with a capacity hint above 2^53 - 1, which both implementations refuse and make no claim for, since a peer running the TypeScript cannot hold the value. A hint of exactly 2^53 - 1 is an ordinary scenario both create.
- `rust_only_frames`: a coordinator frame, given as wire bytes, whose capacity hint is above 2^53 - 1, so the TypeScript decoder cannot hold it and it never reaches a TypeScript election. An election must drop it unevaluated (`rejected`) with no state change, so that a node does not adopt and re-gossip a claim its TypeScript neighbours cannot read. The TypeScript runner reads and counts the list and does not run it.
- `supersedable_terms`: which terms a later claim can supersede. A term of 2^53 - 1 or over cannot, so that an implementation with a double-sized integer and one with a 64-bit integer accept the same claims.
- `device_orders`: the order of two device-ids, `-1`, `0` or `1`, the first differing byte deciding.
- `counts`: the number of entries in each list, which both runners check.

The outcomes are written by hand from the spec, never produced by an implementation, and the device-ids are structural bytes. The TypeScript core's `conformance-coordinator-election.unit.test.ts` and `rust/crates/wire-mesh-conformance` run every scenario against the real election.

## data-sync.v1.json

`data-sync.v1.json` pins the core/data sync primitive (`spec/data-domain.cddl`). Its top-level `vectors` are the `data-have`, `data-request` and `data-entries` frames the scenarios use, round-tripped like any other file. Its `data_sync` section carries its own `layout_version` and holds:

- `scenarios`: each starts a store (`store`: every key with its value in hex, in key order) and runs `steps`. A step names an `op` (`head_seq_for`, `append_own_entry`, `handle_data_have`, `handle_data_request` with its `limit`, `handle_data_entries`, `read_entries`), its input, what it `returns` (a number, the vector name of a frame or `null`, `applied` or `gap`, or the entries read, in hex) and the whole `store` after it, so a stray write fails the scenario. An append also records the `have_frame` it announces.
- `refused_appends`: an append to a log already at the largest sequence a peer holding integers as doubles can hold exactly (2^53 - 1), which both implementations refuse, writing nothing.
- `refused_heads`: a store whose head text is not the plain decimal digits of an integer of at most 2^53 - 1 (empty, not a number, hexadecimal, an exponent, a sign, a fraction, leading zeros, a space, or above the safe integers). Every operation of both implementations (`head_seq_for`, `handle_data_have`, `handle_data_request`, `handle_data_entries`, `read_entries` and `append_own_entry`) refuses it, and the store is unchanged afterwards, so a corrupt head neither reads as an empty log nor is overwritten as one.
- `rust_only_cases`: a frame (as wire bytes) or a stored head carrying an integer above 2^53 - 1, which the TypeScript decoder cannot hold, so the case never reaches its sync functions; the TypeScript runner reads and counts the list and does not run it. A `data-have` or `data-request` carrying such an integer gets no answer (`none`), a `data-entries` frame that starts above it or would reach above it is `rejected` (not a `gap`) and writes nothing. The store is unchanged after every case.
- `counts`: the number of entries in each list, which both runners check.

The log layout is part of the contract: `data/<device-id-hex>/head` holds the head sequence as decimal text and `data/<device-id-hex>/entry/<seq>` one entry, so a store written by either implementation is read by the other. The outcomes are written by hand from the spec, never produced by an implementation, and the device-ids are structural bytes. The TypeScript core's `conformance-data-sync.unit.test.ts` and `rust/crates/wire-mesh-conformance` run every scenario against their data-sync functions.

## file-storage.v1.json

`file-storage.v1.json` pins the layout of the file-backed key-value store both implementations share (the TypeScript `createNodeFsStorage` and the Rust `FsStorage`). It has no wire vectors. Its `file_storage` section carries its own `layout_version` and holds:

- `key_layout`: for each key, the `path` of the file that holds it (relative to the store's directory, `/`-separated) or the `refusal` the layout gives: `empty`, `nul`, `backslash`, `absolute` (a leading slash), `empty_segment` (a doubled or trailing slash), `dot_segment`, `parent_segment` or `drive_prefix` (a segment that starts with an ASCII letter and a colon, which Windows reads as a drive). A key `path.join` would rewrite or that leaves the directory is refused, so it is never stored under another name, and the rules are the same on every host. When a key breaks several rules the first is named, in the order listed here with the segments read from the left. Both implementations' pure layout functions are checked against this list without a filesystem.
- `scenarios`: each starts from a `start` directory (every file under it as a `/`-joined path with its content in hex), runs `steps` on a storage over a copy of it, and records what each returns (`get`: the value in hex, `null` when absent, `refused` for a refused key or `error` for an operating system error such as a key under a file; `set` and `delete`: `ok`, `refused` or `error`; `keys`: the keys under the prefix, sorted, never a file whose name the layout refuses) and the whole `directory` after it, so a stray file or a missing one fails the scenario. A value is the whole content of its file.
- `counts`: the number of entries in each list, which both runners check.

The outcomes are written by hand from the layout, never produced by an implementation. The TypeScript core's `conformance-file-storage.unit.test.ts` and `rust/crates/wire-mesh-conformance` run them: each materialises a `start` directory with plain file operations, so the storage reads what the other implementation writes, and compares the directory back with plain file operations, so what it writes is what the other reads.

## room-params.v1.json

`room-params.v1.json` pins the typed forms of the core/room and capability verbs (`spec/room.cddl`, `spec/management.cddl`) and the helpers their paths are built with. Its top-level `vectors` are manage-request and manage-response frames, round-tripped like any other file. Its `room_params` section carries its own `layout_version` and holds:

- `typed`: for each frame, the `shape` a typed decoder must read it as (`room.send`, `room.read`, `room.leave`, `room.invite`, `capability.request`, or the outcomes `room-join-ok`, `room-members-ok`, `capability-grant-ok`) and every field of it in the form the file records (byte strings as hex, an absent optional as `null`), with the keys of the open tail `* tstr => any` under `extra_keys`. A key the rule names is read as that field and never lands in the tail, and the open tail survives a decode followed by an encode byte for byte.
- `refused`: frames each breaking one rule of a shape (a missing or mistyped field, a negative integer, an integer above 2^53 - 1 in `sent-at`, `at` or `valid-until` (the TypeScript cannot hold it, so the Rust decoder refuses it too; the largest exact value is a `typed` vector), a device-id of the wrong length, a token that is not a COSE_Sign1), which a typed decoder must refuse, each naming the valid `control` vector it varies. A `refused` entry with `rust_only: true` is a frame the Rust decoder refuses and the TypeScript schema accepts (a `message-ref` is a closed map in the CDDL and `messageRefSchema` strips an unknown key), so the TypeScript runner skips it. A request is refused as a whole by the Rust decoder; the TypeScript runner reads the params or outcome through the shape's schema. That `room.read` has at least one message is a verifier obligation of the domain and is not in this list.
- `room_path`: the cases of the room-path and hex helpers. `bytes` and `bytes_refused` are the hex codec, `owner_named` and `dm` build a path (a DM is the sorted pair, and naming one device twice is refused), `parse` takes a path apart (a DM out of order is read as given), and `slug` sanitises a name (a run of characters outside `[A-Za-z0-9_-]` becomes one hyphen and hyphens at either end are trimmed). A refusal carries the name of its reason; the TypeScript helpers throw a message, so its runner checks that they refuse and the Rust binary checks the reason, and fails when a reason has no case.
- `counts`: the number of entries in each list, which both runners check.

The outcomes are written by hand from the spec, never produced by an implementation, and device-ids and tokens are structural bytes. The TypeScript core's `conformance-room-params.unit.test.ts` and `rust/crates/wire-mesh-conformance` run them.

## introspection.v1.json

`introspection.v1.json` pins core/management's `path.trace` and `topology.get` (`spec/management.cddl`) and the `topology-peers` value they and a peer-advert's `topology/peers` gossip extension carry. Its top-level `vectors` are the manage-request and manage-response frames the cases use and gossip frames each holding one peer-advert, round-tripped like any other file. Its `introspection` section carries its own `layout_version` and holds:

- `typed`: for each frame, the `shape` a typed decoder must read it as (`path.trace`, `topology.get`, and the outcomes `path-trace-ok` and `topology-get-ok`) and every field of it, with the keys of the open tail under `extra_keys`.
- `refused`: frames each breaking one rule of a shape (a missing or mistyped field, a device-id of the wrong length, a `peers` that is not a map), which a typed decoder must refuse, each naming the valid `control` vector it varies. A key beyond a closed map is not in this list: the generated TypeScript schemas strip such a key instead of refusing it, so only the Rust decoder's own tests hold it to the rule. A `refused` entry with `rust_only: true` is a frame with a key beyond a closed map (`path.trace` and `topology.get` params, the `peers` map, a relayed entry) that the Rust decoder refuses and the TypeScript schema strips, so the TypeScript runner skips it.
- `path_trace_responses`: the answer built for a `path.trace` that arrived relayed or not, given the hub address the receiver knows. The address is reported only when relayed.
- `trace_cases`: a trace run against a scripted peer and clock (`clock_ms` are the two readings, `reply` the response frame or a closed connection), with the round trip, this side's own relay knowledge, the receiver's reported knowledge, or the failure (`malformed`: an `ok` that is not a `path-trace-ok`; `send`: the connection ended). A round trip is never negative.
- `topology_reads`: the topology read from the `topology/peers` extension of an advert, or `null` for an advert with none or with one that is not a `topology-peers`.
- `topology_graphs`: a directory of adverts and the graph assembled from it: every device is a node, and each device's report gives direct edges and then relay edges, in the order of the directory. Two devices reporting one connection give two edges.
- `topology_get_cases`: `topology.get` run against a scripted peer: the peers, a refusal with its code, a malformed answer, or a send failure.
- `counts`: the number of entries in each list, which both runners check.

The outcomes are written by hand from the spec, never produced by an implementation. Device-ids, keys and signatures are structural bytes and the adverts are not verified. The TypeScript core's `conformance-introspection.unit.test.ts` and `rust/crates/wire-mesh-conformance` run them.

## gossip-directory.v1.json

`gossip-directory.v1.json` pins what a session does with the gossip it receives and sends. Its top-level `vectors` are the gossip frames the scenarios deliver. The adverts are really signed, with the Ed25519 keys under `identities` (fixed secrets, so every run writes the same bytes). The `gossip_directory` section holds:

- `identities`: the keys the adverts are signed with, each with its secret, public key and device id; `me` is the node the scenarios run as.
- `extension_validation`: key bags a gossip update may carry, each accepted or refused for one named reason (`reserved_field`, `session_managed`, `reserved_version`, `not_domain_qualified`), naming the first key refused.
- `directory_scenarios`: gossip frames delivered in order. Each step gives what became of every advert in it (`admitted`, `older`, or the reason it was refused: `wrong_device`, `bad_signature`) and the directory held afterwards, as the device and snapshot time of each entry in first-heard order. A scenario with `rust_only` pins a bound only the Rust session applies (the advert size cap): the TypeScript runner skips it. The TypeScript session reports no per-advert outcome, so its runner compares the directory only.
- `self_adverts`: the advert a session builds for a given clock and extension bag: its device, addresses, `snapshot-seconds`, the sorted keys of its open tail (the extensions, `topology/peers` and `wire-mesh/version`) and its topology. Each is signed by `me` and verifies. The version's value is not pinned, since it is each implementation's own.
- `counts`: the number of entries in each list, which both runners check.

The outcomes are written by hand from the rules of the session, never produced by an implementation. The TypeScript core's `conformance-gossip-directory.unit.test.ts` and `rust/crates/wire-mesh-conformance` run them.

`verify.unit.test.ts` checks only the round trip every vector file shares: this package holds no protocol implementation of its own, so `signing_input_hex`, `verifies` and the `secure_channel` section are checked by the implementations. `ts/packages/core`'s own conformance tests check them for the TypeScript. The Rust binary checks every file: the round trip of each, `adverts.v1.json`'s extra fields, and `secure-channel.v1.json`'s `secure_channel` section, which it recomputes from the fixed inputs and runs step by step against `wire_mesh_core::domain::secure_channel` (the intermediate keys, every sealed ciphertext, every verdict and every open step with its expected class), failing on any field of the section it does not read.

## Regenerating

```
pnpm install
pnpm run generate   # rebuilds codec.ts first, then writes {handshake,tokens,adverts,frames,secure-channel}.v1.json from generate.ts's vector definitions
pnpm test            # rebuilds codec.ts first, then decodes every committed vector and confirms it round-trips
```

`generate.ts` holds the vector definitions and is the actual source of truth, not the JSON files; `adverts.ts` holds `adverts.v1.json`'s own, which need real key material rather than filler, `secure-channel-vectors.ts` holds `secure-channel.v1.json`'s, and `vector-files.ts` holds the writer and each output file's description. All three are split apart because generate.ts sits at this repo's own max-lines cap, not because they are conceptually separate stages: every vector's `message` is authored as plain TypeScript data matching a CDDL rule's fields, and `wire_hex` is derived mechanically by canonically CBOR-encoding it via [`cbor2`](https://www.npmjs.com/package/cbor2)'s CDE (CBOR Common Deterministic Encoding) mode -- the RFC 8949 4.2 core deterministic rules DAG-CBOR itself builds on -- never hand-typed. CI regenerates and diffs against the committed files the same way `spec/`'s own `cddl-validate` job does for `protocol.cddl`, so the two can never silently drift apart.

## Tasks, caching, and linting

`build`/`generate`/`test`/`typecheck`/`lint` are each a thin public script that calls `turbo run _<name>` -- e.g. `"build": "turbo run _build"`, `"_build": "tsdown"`. `turbo.json` keys its task graph on those same underscore names (never the public ones: a task literally named `build` would make `pnpm run build`'s own `turbo run build` call resolve straight back to itself, the recursive-call case Turborepo's docs warn against). `generate`/`test`/`typecheck`/`lint` all depend on `build`, so any of them rebuilds `codec.ts` first when something it depends on changed, and replays the cached result when nothing did -- running several in one invocation (`pnpm turbo run _generate _test _typecheck _lint`, what `just conformance` does) still only builds once, deduplicated across every task that needs it.

Linting uses [`@exadev/eslint-config`](https://www.npmjs.com/package/@exadev/eslint-config), the org's shared config, plus Prettier via `eslint-plugin-prettier`. Typed lint rules need `dist/`'s declarations to resolve the self-referenced package import, which is exactly why `_lint` depends on `_build` too.

## codec.ts is a real, polymorphic package, not just a shared file

`codec.ts` defines the one JSON convention every vector's `message` needs: since JSON has no byte-string type, a CDDL `bstr` field is written as `{ "hex": "<lowercase hex>" }` rather than a raw string or number array. `toWire`/`fromWire` convert between that marker shape and the real bytes CBOR needs on the way in and out; `isVectorFile` validates a parsed vector file at the JSON boundary rather than trusting an `as` cast.

`generate.ts` and `verify.unit.test.ts` both import it as `@exadev/wire-mesh-conformance` (self-referencing the package by its own name), not via a relative path -- `pnpm run build` (`tsdown`) compiles `codec.ts` into dual ESM/CJS output plus `.d.mts`/`.d.cts` declarations under `dist/`, and `package.json`'s `exports` map is what makes the self-reference resolve to that built output rather than the source file. This means the same artifact every consumer would actually get is what runs here, not a stand-in. [`@arethetypeswrong/cli`](https://github.com/arethetypeswrong/arethetypeswrong.github.io) (wired into the `build` script via `tsdown`'s own `attw` option) checks that dual-package surface resolves correctly under Node's `node16` module resolution -- catching the class of "works in this repo, broken for a real consumer" bug that a bare `tsc` build can't see, before it ever has to matter.

Node (26+) runs every `.ts` file here directly via its own native TypeScript support -- no `tsx`/`ts-node` needed. `tsconfig.json` sets `moduleResolution: "nodenext"` to match that reality, and is scoped to `codec.ts` alone (`"include": ["codec.ts"]`) since that's the one file `tsdown` actually builds -- anything else in this scope (a script's own top-level await, a config file's own type shape) would otherwise leak into what gets type-checked as part of the *build*. Everything else (`generate.ts`, `verify.unit.test.ts`, `tsdown.config.ts`, `eslint.config.ts`) is covered by `tsconfig.node.json` instead, which extends `tsconfig.json`. `pnpm run typecheck` runs both.

Signature and public-key bytes throughout are clearly-synthetic filler (`aa`/`bb`/`ee`/`ff`-repeated hex), not real cryptographic material -- these vectors freeze the wire-exact envelope shape (map key ordering, field presence, the recursive delegation-chain nesting), not a working signature, the same scope Cascade's own frozen vectors commit to for fields with no real crypto behind them.

## Gotcha: `cbor2` doesn't recognise a Node `Buffer` as a byte string

Feeding a plain Node `Buffer` (rather than a plain `Uint8Array`) into `cbor2`'s `encode()` silently produces the wrong output: `Buffer` overrides `toJSON()`, and `cbor2`'s type dispatch falls through to a generic-object encoder that serialises it as a garbled `{ type: "Buffer", data: [...] }` CBOR map instead of a byte string, with no error raised. Confirmed directly while writing this generator -- caught only because the verifier's round-trip check failed with an unreadable diff. `toWire()` in `codec.ts` guards against this explicitly, converting every marker to a genuine `Uint8Array` via `Uint8Array.from(Buffer.from(hex, "hex"))` rather than passing a `Buffer` straight to `encode()`.

## Gotcha: `typescript` is pinned below 6.1, not left on latest

`typescript-eslint` (which `@exadev/eslint-config` depends on) does not yet support TypeScript 7 -- confirmed directly, `eslint` fails outright with "typescript-eslint does not support TS 7.0" against the latest `typescript` release. `typescript` is pinned to `6.0.3`, the newest release still inside `typescript-eslint`'s own `>=4.8.4 <6.1.0` peer range, rather than left on latest -- this is the documented-incompatibility exception the org's own dependency convention already carves out for exactly this situation. Bump it back to latest once [typescript-eslint#10940](https://github.com/typescript-eslint/typescript-eslint/issues/10940) ships support for TS 7.

## mint.v1.json

`mint.v1.json` pins what a conformant minter produces and refuses (`spec/tokens.cddl`, `spec/management.cddl`). Its top-level `vectors` are every minted token and revocation entry, and every `fixture_*` token (a token someone holds, signed as written, which a mint would never produce and which a case cites as a parent or an authoriser), round-tripped like any other file. Its `mint` section holds the inputs of each case and the expected outcome, with its own `layout_version`:

- `identities`: Ed25519 identities (`secret_hex`, public key and device-id, each marked `synthetic: true`), whose signatures are deterministic, so a minter given the same inputs produces the same bytes.
- `token_mints`: each case lists every input of a mint (issuer, clock, token-id, bearer, verb, scope, expiry, optional not-before, delegations-remaining, conditions, the whole COSE_Sign1 of a parent or an authorising grant-capability, grants-capability and requests-capability, with `null` for an absent optional) and expects either `minted` (the vector holding the exact token, and `verifies`, whether it verifies on its own at the file's clock) or `refused` with one reason. `rust_only` marks the cases that expect `value_not_representable`, the refusal of an integer above 2^53 - 1 that only an implementation with a Rust-sized integer can give: the TypeScript runner skips them, and a case at 2^53 - 1 mints in both.
- `revocation_mints`: the exact entry minted from an identity, a token-id and a revoked-at.
- `notice_mints`: the exact room notice created by a poster from a room, the vector of the poster's own `room:member` token (embedded in full), a notice-id, a content-type and content, optional references, expiry and key epoch, at a clock whose reading becomes `posted-at`. The expected `verdict` is what the room's owner (identity `a`, the root of both posters' tokens) gives it: `valid`, or the refusal. A notice whose key epoch does not pair with its content-type is created all the same and refused by the reader (`key_epoch_mismatch`), because creation checks nothing.
- `can_grant` and `can_grant_via`: the verdict of the two pure queries for a held token, a device and a candidate (and a bearer, for the authorised-by form).
- `counts`: how many cases each list holds. Both runners fail when a list holds another number, so a case that vanishes from the file cannot go unnoticed.

The conditions of an authorising grant-capability give two different refusals, as trilean's schema decides: a node the schema rejects (`exists` without its operand, an unknown kind, a field of the wrong type) is `authorisation_malformed`, and a node the schema accepts that an implementation cannot evaluate (a comparison against a `reference`) is indeterminate, so `authorisation_conditions_not_satisfied`. trilean's node schemas strip a key they do not name (only the two complex literals are strict), so a node with an extra key is read as the node without it, in a token's own conditions and in an authoriser's. The Rust decoder keeps the two apart; for a kind it does not evaluate it checks only that every required field is present, so a node of such a kind with the right fields of the wrong type reads there as unevaluable where the TypeScript rejects it. A number that is not an integer cannot be represented by the Rust wire value, so a list holding one fails to decode there and is `authorisation_malformed`, where the TypeScript evaluates it.

How the refusals are pinned. The refusals of a mint run in a fixed order, and each case breaks the rules it names and no others, except the order cases. The generator lists every condition that can produce a refusal (each disjunct of each rule) with the one case that breaks it, and throws when a named case does not exist. It builds one case per neighbouring pair of rules in each chain of rules (the checks that run before the links, the parent link, the authorised-by link), each breaking both rules and expecting the earlier reason, and throws when a pair is neither generated nor listed as one whose rules cannot both be broken in one token (a parent that does not decode has no bearer, an authoriser that does not decode has no parent, conditions that do not decode cannot be evaluated). Both runners also fail when a refusal reason has no case.

The scope rule is the TypeScript core's: a parent path that ends in `/` already names a segment boundary, so everything under it narrows it (the root `/` included), and a path with a `.` or `..` segment never narrows anything.

A token's protected header carries its `alg` and `kid` under the text keys `"1"` and `"4"`, which is what the frozen vectors and the TypeScript core write and every verifier reads (RFC 9052 names the integer labels; moving both implementations to them is a change of the signed bytes). The generator builds each token from the spec text with node:crypto alone, and the expected refusal of each case is written by hand, so the vectors check an implementation against the spec and not against itself. Each implementation's own tests check them: `ts/packages/core/test/conformance-mint.unit.test.ts` and `rust/crates/wire-mesh-conformance`.
